ARTICLE 1 — PROJECT DESCRIPTION AND SCOPE

1.1 Project Objectives. The Client has engaged the Provider to design, develop, test, and deliver a new Core Ledger Module (the "Module") that will replace the Client's legacy double-entry general ledger subsystem within the Client's core banking platform. The Module shall (a) maintain a fully auditable double-entry ledger across all of the Client's chart-of-accounts entities, (b) support intraday balance computation with sub-second latency at the Client's peak transaction throughput of fifteen thousand (15,000) transactions per second, (c) integrate with the Client's existing payment, deposit, and lending subsystems via the published API contracts referenced in Schedule A, (d) support the Client's regulatory reporting obligations under the Federal Financial Institutions Examination Council (FFIEC) Call Report instructions, and (e) be delivered as production-grade source code under the Provider's source code escrow arrangement.

1.2 In-Scope Activities. Subject to the Assumptions in Article 6, the Provider shall perform the following In-Scope Activities:

(a) Discovery and Requirements. Collaborative discovery sessions with the Client's banking platform engineering team, leading to a written Requirements Specification covering functional requirements, non-functional requirements (latency, throughput, availability), interface contracts, and regulatory compliance requirements.

(b) Module Design. Architectural and detailed design of the Module, including the data model, the transaction processing pipeline, the consistency model, the recovery model, and the integration interfaces. Design artifacts shall be delivered in the form of an Architecture Specification and a Detailed Design Document.

(c) Module Implementation. Implementation of the Module in the programming language and runtime environment specified in the Requirements Specification, following the Provider's secure software development lifecycle and the Client's coding standards.

(d) Unit and Integration Testing. Implementation of unit tests covering at least eighty-five percent (85%) line coverage of the Module's business logic, plus integration tests against test doubles for each of the Client's downstream subsystems.

(e) Performance Testing. Performance testing against the Client's peak throughput target, with results documented in a written Performance Test Report.

(f) Security Testing. Internal application security review by the Provider's security team, including SAST, dependency vulnerability scanning, and threat modeling. The Provider shall also coordinate with the Client's third-party penetration testing vendor to support the Client's penetration test of the Module.

(g) Production Cutover Support. Support for the Client during the production cutover from the legacy ledger to the Module, including the data migration of opening balances and the parallel-run validation period of fifteen (15) business days.

(h) Source Code Escrow. Deposit of the Module source code with the source code escrow agent identified in Schedule B, in accordance with the source code escrow agreement attached as Schedule B-1.

1.3 Out-of-Scope Activities. The following are expressly out-of-scope and not included in the Project Fee. Any of the following, if requested, requires a Change Order under Article 8:

(a) Migration of any historical ledger data from the legacy system. Historical data migration is being performed by a separate vendor under a separate engagement, and the Provider shall coordinate with that vendor but shall not perform the migration itself.

(b) Implementation of any features not described in the Requirements Specification.

(c) Customer-facing user interface or operator console for the Module. The Module is a back-end service exposing API contracts; any UI is the Client's responsibility.

(d) Integration with any third-party regulatory reporting vendor. The Provider shall produce the data feeds required by the Call Report instructions; mapping the Client's data to a third-party reporting vendor's input format is the Client's responsibility.

(e) Any work product subject to U.S. export control restrictions other than EAR99 commercial software.

(f) Provision of any production cloud infrastructure or hosting services. The Module will run on the Client's infrastructure.

1.4 Engagement Period. The Provider shall perform the In-Scope Activities during the period beginning on the Project Start Date and ending on the Project End Date set forth in Article 3.

ARTICLE 2 — DELIVERABLES AND ACCEPTANCE

2.1 Deliverables. The Provider shall produce and deliver to the Client the following deliverables (each a "Deliverable" and collectively the "Deliverables"):

(a) Requirements Specification — a written specification covering functional and non-functional requirements, interface contracts, and regulatory compliance requirements. Target delivery: end of Project Week 6.

(b) Architecture Specification — a written specification of the Module's architecture. Target delivery: end of Project Week 10.

(c) Detailed Design Document — a written document describing the data model, the transaction processing pipeline, the consistency model, and the recovery model. Target delivery: end of Project Week 14.

(d) Module Source Code, Phase 1 (Core Posting Engine) — production-grade source code for the core posting engine, with unit tests and inline documentation. Target delivery: end of Project Week 22.

(e) Module Source Code, Phase 2 (Integration Layer) — production-grade source code for the integration layer connecting the Module to the Client's downstream subsystems. Target delivery: end of Project Week 30.

(f) Module Source Code, Phase 3 (Reporting Feeds) — production-grade source code for the regulatory reporting data feeds. Target delivery: end of Project Week 36.

(g) Performance Test Report — a written report documenting the results of performance testing against the Client's throughput targets. Target delivery: end of Project Week 38.

(h) Security Review Report — a written report documenting the Provider's internal security review and the resolution of any findings from the Client's third-party penetration test. Target delivery: end of Project Week 40.

(i) Production Cutover Report — a written report documenting the production cutover and the parallel-run validation results. Target delivery: end of Project Week 44.

2.2 Acceptance Criteria. Acceptance criteria for each Deliverable are set forth in Schedule A. For source code Deliverables (Sections 2.1(d), (e), (f)), acceptance criteria include (i) successful build and unit test execution in the Client's continuous integration environment, (ii) passing of the unit test coverage threshold, (iii) passing of the static analysis quality gate, (iv) absence of any critical or high severity vulnerabilities in dependency scans, and (v) the Provider's written attestation that the Module functions as specified in the Requirements Specification.

2.3 Acceptance Period. The Client shall have a period of fifteen (15) business days following its receipt of each Deliverable (the "Acceptance Period") to review the Deliverable and notify the Provider in writing of either (a) acceptance, or (b) rejection accompanied by a written description of the alleged non-conformity with the acceptance criteria. For source code Deliverables, the Acceptance Period shall be twenty (20) business days to accommodate the Client's internal code review process.

2.4 Cure of Non-Conformity. If the Client rejects a Deliverable, the Provider shall, at no additional charge to the Client, correct the alleged non-conformity and resubmit the corrected Deliverable to the Client within fifteen (15) business days of receipt of the Client's rejection notice. The Client shall then have a new Acceptance Period to review the resubmitted Deliverable. If the Provider fails to deliver a conforming Deliverable after three (3) cycles of cure (the additional cure cycle reflects the technical complexity of the Module), the Client may, at its option, (i) accept the Deliverable in its then-current form with an equitable reduction in the Project Fee attributable to such Deliverable, (ii) terminate this SOW for material breach pursuant to the termination provisions of the MSA, or (iii) require the Provider to engage at the Provider's expense a third-party developer reasonably acceptable to the Client to complete the rejected Deliverable.

2.5 No Deemed Acceptance. There shall be no deemed acceptance of any Deliverable. Any Deliverable not affirmatively accepted by the Client in writing within the Acceptance Period shall remain unaccepted.

2.6 Source Code Escrow Deposit Verification. As a condition of acceptance of each source code Deliverable, the Provider shall deposit the source code with the escrow agent within ten (10) business days following the Client's acceptance, and shall provide the Client with the escrow agent's deposit confirmation. Failure to make a timely escrow deposit shall be a material breach of this SOW.

ARTICLE 5 — CLIENT RESPONSIBILITIES

The Client shall designate, prior to the Project Start Date, (a) an Executive Sponsor (the Client's Chief Technology Officer or designee) with authority to make Project-level decisions, (b) a Client Project Manager who will serve as the day-to-day point of contact for the Provider, (c) a Banking Platform Architect responsible for the integration interfaces between the Module and the Client's existing subsystems, and (d) a Compliance Liaison responsible for the regulatory reporting requirements.

5.2 Access to Systems and Data. The Client shall provide the Provider with timely access to (a) the Client's continuous integration and source code management environments, (b) the Client's testing environment for the Module, (c) read-only access to the Client's existing core banking platform documentation and API contracts, and (d) such physical and logical access as the Provider reasonably requires. 5.5 Client Delays. If the Client fails to satisfy any of its responsibilities under this Article 5 in a timely manner, and such failure prevents or delays the Provider from performing the In-Scope Activities, the Provider shall be entitled to (a) an extension of the relevant Milestone target completion date and the Project End Date by a number of business days equal to the duration of the Client's delay, and (b) reimbursement of any reasonable, documented additional costs the Provider incurs as a direct result of the Client Delay.

ARTICLE 6 — ASSUMPTIONS AND DEPENDENCIES

6.1 Assumptions. The Project Fee, the Project Schedule, and the In-Scope Activities are based on each of the following assumptions (the "Assumptions"). If any Assumption proves materially incorrect, the affected impact on scope, schedule, or fees shall be addressed through the change control procedure in Article 8.

(a) The Client's published API contracts referenced in Schedule A are stable and complete as of the Project Start Date. Any breaking changes to those API contracts during the Project Period shall constitute a change in scope.

(b) The Client's existing core banking platform supports the throughput target of fifteen thousand (15,000) transactions per second under the existing infrastructure capacity. The Provider's performance testing shall validate the Module's contribution to this target; end-to-end platform throughput is the Client's responsibility.

(c) The Client's regulatory reporting requirements remain substantially as described in the FFIEC Call Report instructions in effect as of the Project Start Date. Any material changes to those instructions during the Project Period shall constitute a change in scope.

(d) The Client's continuous integration environment, source code management system, and testing environment are operational and suitable for the Module's build and test workflow as of Project Week 4.

(e) The Client's third-party penetration testing vendor will conduct its penetration test of the Module within ten (10) business days following the Client's acceptance of the Phase 3 Source Code (Milestone 6).

(f) The legacy ledger subsystem will remain operational during the parallel-run validation period to support the comparison of legacy and Module results.

(g) No regulatory examinations, supervisory actions, or consent orders affecting the Client's core banking platform will require the Provider to suspend or materially modify the In-Scope Activities during the Project.

6.2 Third-Party Dependencies. The Project depends on the continued availability and proper functioning of (a) the Client's continuous integration and source code management environments, (b) any third-party libraries or open-source components incorporated into the Module (subject to the Provider's open-source compliance review), and (c) the source code escrow agent's services.

6.3 Notification of Changed Assumptions. The Client shall promptly notify the Provider in writing if it becomes aware that any Assumption has changed or is no longer valid.
