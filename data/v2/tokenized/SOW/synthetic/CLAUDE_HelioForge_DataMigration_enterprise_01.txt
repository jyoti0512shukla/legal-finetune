ARTICLE 1 — PROJECT DESCRIPTION AND SCOPE

1.1 Project Objectives. The Client has determined to retire its legacy Oracle Database 12c environment and migrate the data, schemas, and dependent application interfaces to a Snowflake cloud data platform tenant operated by the Client. The Provider shall perform the data migration, schema conversion, ETL pipeline rebuild, validation, and cutover services described in this Article 1, the purpose of which is to enable the Client to (a) decommission the legacy Oracle environment by the Project End Date, (b) achieve no greater than four (4) hours of cutover downtime for each migrated production workload, and (c) preserve referential integrity and historical reporting continuity across the migrated datasets.

1.2 In-Scope Activities. Subject to the Assumptions set forth in Article 6, the Provider shall perform the following activities (the "In-Scope Activities"):

(a) Discovery Phase. Conduct a structured discovery of the Client's existing Oracle 12c environment, including a catalog of databases, schemas, tables, views, stored procedures, materialized views, scheduled jobs, triggers, and ETL pipelines feeding the environment. The Discovery Phase shall produce a written Discovery Report (a Deliverable under Article 2).

(b) Target Architecture Design. Design the target Snowflake architecture, including warehouses, databases, schemas, role-based access control, network policies, masking policies, data sharing configurations, and resource monitors. The Target Architecture Design shall be documented in a written Architecture Specification (a Deliverable under Article 2).

(c) Schema Conversion. Convert Oracle schemas to Snowflake-compatible schemas, including mapping of Oracle data types to Snowflake equivalents, conversion of stored procedures and packages from PL/SQL to Snowflake SQL or JavaScript user-defined functions, and remediation of any Oracle-specific syntax incompatibilities.

(d) ETL Pipeline Rebuild. Rebuild the existing Informatica PowerCenter ETL pipelines as Snowpipe-based ingestion pipelines or as Snowflake tasks-and-streams, depending on the source system characteristics for each pipeline.

(e) Data Migration and Validation. Perform full and incremental data loads from the legacy Oracle environment to Snowflake, and execute the Data Validation Plan set forth in the Architecture Specification, including row-count reconciliation, hash-based content validation on sampled tables, and reconciliation of aggregate financial reporting metrics against pre-migration baselines.

(f) Cutover and Hypercare. Coordinate with the Client to schedule and execute the production cutover for each migrated workload, and provide hypercare support for thirty (30) calendar days following cutover, including incident triage, root-cause analysis, and remediation of any data integrity issues directly attributable to the migration.

(g) Knowledge Transfer. Conduct knowledge transfer sessions for the Client's data engineering team and produce written runbooks documenting the migrated environment, the validation procedures, and the rollback procedures.

1.3 Out-of-Scope Activities. The following are expressly out-of-scope and not included in the Project Fee, and the Provider shall have no obligation to perform any of them under this SOW:

(a) Migration of any data sources other than the legacy Oracle 12c environment identified in the Discovery Report. Migration of additional source systems, if requested, requires a Change Order under Article 8.

(b) Refactoring, rewriting, or modernizing the application code that connects to the migrated data. The Provider's responsibility ends at the data layer; application-side changes are the Client's responsibility.

(c) Procurement, configuration, or operation of the Client's Snowflake account, including any Snowflake credit consumption charges (which the Client pays directly to Snowflake Inc.).

(d) End-user training on the Snowflake platform, beyond the knowledge transfer sessions described in Section 1.2(g).

(e) Migration of unstructured data, file shares, document repositories, image stores, or any data not stored in the legacy Oracle 12c environment.

(f) Any work product subject to export-control restrictions under the International Traffic in Arms Regulations (ITAR) or the Export Administration Regulations (EAR).

(g) Custom development of new analytics, dashboards, or reporting capabilities not present in the legacy environment.

1.4 Engagement Period. The Provider shall perform the In-Scope Activities during the period beginning on the Project Start Date and ending on the Project End Date set forth in Article 3, subject to extensions agreed in any executed Change Order.

ARTICLE 2 — DELIVERABLES AND ACCEPTANCE

2.1 Deliverables. The Provider shall produce and deliver to the Client the following deliverables (each a "Deliverable" and collectively the "Deliverables"):

(a) Discovery Report — a written report describing the existing Oracle environment, the source systems, the data volumes, the dependencies, and any risks or issues identified during the Discovery Phase. Target delivery: end of Project Week 4.

(b) Architecture Specification — a written specification of the target Snowflake architecture, including the Data Validation Plan and the Cutover Plan. Target delivery: end of Project Week 8.

(c) Migration Test Report — a written report documenting the results of the data validation runs against a non-production replica of the production environment, including row-count reconciliations and hash validation results. Target delivery: end of Project Week 16.

(d) Production Cutover Report — a written report documenting the production cutover, including the actual cutover window, any incidents encountered, and the post-cutover validation results. Target delivery: within five (5) business days after each production cutover.

(e) Hypercare Closure Report — a written report documenting the hypercare period, including any incidents reported, root-cause analyses, and remediation actions taken. Target delivery: end of Project Week 22.

(f) Operational Runbooks — written runbooks documenting the migrated environment, validation procedures, and rollback procedures for the Client's data engineering team. Target delivery: end of Project Week 24.

2.2 Acceptance Criteria. Acceptance criteria for each Deliverable are set forth in the table in Schedule A. Each Deliverable shall be deemed conforming if it satisfies the acceptance criteria for that Deliverable.

2.3 Acceptance Period. The Client shall have a period of ten (10) business days following its receipt of each Deliverable (the "Acceptance Period") to review the Deliverable and notify the Provider in writing of either (a) the Client's acceptance of the Deliverable, or (b) the Client's rejection of the Deliverable, accompanied by a written description of the alleged non-conformity with the acceptance criteria.

2.4 Cure of Non-Conformity. If the Client rejects a Deliverable, the Provider shall, at no additional charge to the Client, correct the alleged non-conformity and resubmit the corrected Deliverable to the Client within ten (10) business days of receipt of the Client's rejection notice. The Client shall then have a new Acceptance Period to review the resubmitted Deliverable. If the Provider fails to deliver a conforming Deliverable after two (2) cycles of cure, the Client may, at its option, either (i) accept the Deliverable in its then-current form with an equitable reduction in the Project Fee attributable to such Deliverable, or (ii) terminate this SOW for material breach pursuant to the termination provisions of the MSA and recover the portion of the Project Fee paid for the rejected Deliverable.

2.5 No Deemed Acceptance. Notwithstanding anything to the contrary in the MSA, no Deliverable under this SOW shall be subject to deemed acceptance. Any Deliverable not affirmatively accepted by the Client in writing within the Acceptance Period shall remain unaccepted, and the passage of time alone shall not constitute acceptance. The Parties have agreed to this no-deemed-acceptance treatment in light of the regulated reporting and auditability requirements applicable to the migrated workloads.

ARTICLE 6 — ASSUMPTIONS AND DEPENDENCIES

6.1 Assumptions. The Project Fee, the Project Schedule, and the In-Scope Activities are based on each of the following assumptions (the "Assumptions"). If any Assumption proves materially incorrect, the affected impact on scope, schedule, or fees shall be addressed through the change control procedure in Article 8.

(a) The legacy Oracle 12c environment contains no more than fifteen (15) production databases and a total data volume of no more than twenty (20) terabytes as of the Project Start Date. Any additional databases or data volume in excess of these thresholds shall constitute a change in scope.

(b) The Client's source data is sufficiently clean and well-documented that the Provider will not be required to perform substantive data cleansing or data quality remediation as part of the In-Scope Activities. Substantive data cleansing, if required, shall constitute a change in scope.

(c) The Client's existing application code that connects to the legacy Oracle environment can be repointed to the new Snowflake environment without material refactoring, by means of connection-string and driver changes only. Application-side code changes are out-of-scope per Section 1.3(b) regardless.

(d) The Client's existing Informatica PowerCenter ETL pipelines are documented sufficiently for the Provider to convert them to Snowflake-native pipelines without reverse-engineering the underlying business logic.

(e) The Client's Snowflake tenant is provisioned and operational prior to the Project Start Date, with sufficient credits and warehouse capacity for the test and migration runs contemplated by the Architecture Specification.

(f) The Client's Subject Matter Experts will be available to the Provider for an average of eight (8) hours per week throughout the Project.

(g) No regulatory examinations, audits, or supervisory actions affecting the Client's data environment will require the Provider to suspend or materially modify the In-Scope Activities during the Project.

6.2 Third-Party Dependencies. The Project depends on the continued availability and proper functioning of (a) the Snowflake cloud data platform operated by Snowflake Inc., (b) any third-party connector or driver software used in the migration, and (c) any third-party data quality, lineage, or observability tools the Client requires the Provider to integrate with. The Provider shall not be responsible for any delay or failure of performance to the extent caused by the failure of any such third-party dependency.

6.3 Notification of Changed Assumptions. The Client shall promptly notify the Provider in writing if it becomes aware that any Assumption has changed or is no longer valid. The Provider shall similarly notify the Client if it becomes aware during the Project that any Assumption has proven incorrect.
