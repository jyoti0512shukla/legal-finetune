ARTICLE 1 — PROJECT DESCRIPTION AND SCOPE

1.1 What we're building

The Provider is building a native iOS app for the Client's existing B2B SaaS product. The app gives the Client's end users the same core workflow they have on the web — create, view, edit, and share — but optimized for mobile use cases (push notifications, offline support, biometric auth, share sheet integration). The Project covers design, build, App Store submission, and a 30-day post-launch hypercare period.

1.2 In-scope (T&M with NTE cap)

The Provider will:

(a) Run a 1-week design sprint to translate the Client's existing web product into mobile-native screens for the core workflow.

(b) Build the iOS app in Swift with SwiftUI, targeting the latest iOS major version and the prior major version.

(c) Implement the core workflow screens: sign-in (including SSO and biometric), home, list view, detail view, create/edit, share, settings, profile.

(d) Implement push notifications via APNs for the Client's existing notification events.

(e) Implement offline read-only support: cached recent items viewable without network.

(f) Implement biometric auth (Face ID / Touch ID) for app unlock.

(g) Integrate with the Client's existing API (the API contracts in Schedule A).

(h) Build automated tests: unit tests for business logic, snapshot tests for the major screens, basic UI tests for the critical user flows.

(i) Submit the app to the App Store under the Client's existing Apple Developer account, working through any App Store review feedback to first acceptance.

(j) Provide 30 calendar days of post-launch hypercare with daily standups during the first week and weekly office hours during weeks 2-4.

1.3 Out-of-scope

(a) Android. Web. Apple Watch. iPad-specific layouts (the iPhone app will run on iPad in compatibility mode but is not optimized for iPad).

(b) Backend / API changes. The Provider builds against the Client's existing API as documented in Schedule A. If the Client's existing API doesn't support a needed mobile feature, that's a Change Order.

(c) Push notification server infrastructure. The Provider integrates with the Client's existing notification system; the Provider does not build new server infrastructure.

(d) Offline write or sync support. Only offline read of cached recent items is in scope.

(e) In-app purchases or subscription management.

(f) Localization beyond US English.

(g) Custom analytics or product analytics integration beyond a single basic events SDK (Mixpanel, Amplitude, or Segment — Client picks).

(h) App Store screenshots, promotional graphics, marketing copy, or App Store optimization. The Client provides these.

(i) Apple Developer account setup or App Store team management. The Client owns the Apple Developer account.

(j) Multi-environment build configuration beyond development and production.

ARTICLE 2 — DELIVERABLES AND ACCEPTANCE

2.1 Deliverables

(a) Design Sprint Deliverable — Figma screens for the core workflow, reviewed and signed off by the Client before build starts. Target: end of Project Week 2.

(b) Build Phase 1 — Sign-In and Home Screen — running app build with sign-in (including SSO, biometric) and home screen. Target: end of Project Week 5.

(c) Build Phase 2 — List, Detail, Create/Edit Screens — running app build with the core CRUD workflow. Target: end of Project Week 9.

(d) Build Phase 3 — Push Notifications, Offline Support, Share Sheet — running app build with the remaining mobile-native features. Target: end of Project Week 12.

(e) Test Suite Complete — unit tests, snapshot tests, and UI tests passing in CI. Target: end of Project Week 13.

(f) App Store Submission — TestFlight build submitted to App Store Review. Target: end of Project Week 14.

(g) App Store First Acceptance — app accepted by App Store Review (may require multiple submissions to address review feedback). Target: end of Project Week 16.

(h) Hypercare Closure Report — written report covering the 30-day hypercare period. Target: end of Project Week 20.

2.2 Acceptance window

5 business days for build deliverables (the Client's QA team installs the TestFlight build and exercises the in-scope flows). 10 business days for the Hypercare Closure Report. If the Client doesn't respond within the acceptance window, the Provider sends a written reminder; if still no response within 3 business days after the reminder, the Deliverable is deemed accepted.

2.3 Cure of non-conformity

The Provider has 5 business days to fix and re-deliver each build deliverable. After two cure cycles on a single Deliverable, the Client may either accept with an equitable Project Fee reduction or escalate via the MSA's dispute resolution procedures.

2.4 App Store review feedback

App Store Review may require code changes to address Apple's review feedback. Working through Apple's review feedback to first acceptance is in scope. If Apple's feedback requires substantive changes to the in-scope features (e.g., Apple rejects the entire app architecture, Apple requires a feature change that wasn't anticipated), the affected scope may need a Change Order.

5.3 Client delays

Persistent delays of more than 10 cumulative business days entitle the Provider to additional T&M charges for re-mobilization at the rate card in Schedule B.

ARTICLE 6 — ASSUMPTIONS AND DEPENDENCIES

6.1 Assumptions

(a) The Client's existing API is complete and supports the mobile-native features in scope (push, offline read, biometric, SSO). The Provider relies on the API contracts in Schedule A and has not independently verified API completeness.

(b) The Client's API uses standard OAuth 2.0 / OpenID Connect for authentication, including SSO via the Client's existing identity provider.

(c) The Client owns the Apple Developer account and has the App Store listing already created (or is willing to create it during the engagement).

(d) The Client has the rights to all assets used in the app (logos, icons, copy). The Provider relies on the Client's representations and does not perform independent IP clearance.

(e) The app's core workflow can be implemented with the standard SwiftUI component set and a single push-notification SDK. Custom UI components or complex animations beyond standard SwiftUI capabilities may require a Change Order.

(f) Apple's App Store Review Guidelines as published as of the Project Start Date remain materially unchanged during the Project. Material changes to App Store Review Guidelines that require app rework are addressable via Change Order.

(g) The Client doesn't require the app to support iOS versions older than the latest two major versions.

6.2 Third-party dependencies

The Project depends on (a) the Client's existing API being available and stable, (b) Apple's App Store Connect and TestFlight services being operational, (c) any third-party SDKs the Provider uses (auth library, push notification SDK, analytics SDK) being available and supported, and (d) the Client's identity provider supporting mobile SSO.

6.3 If an assumption is wrong

The Provider notifies the Client promptly upon discovering any incorrect assumption.

8.5 De minimis
